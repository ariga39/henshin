# Backup, Archival Retention, and Recovery

This topic owns application backup scope, publication, retention, long-term archives, recovery procedures and restore evidence. [Persistence](data-model.md) owns SQLite constraints and consistent snapshots; [consistency](synchronization.md) owns instance/epoch/history semantics; [deployment](architecture.md) owns credentials and stopped-service maintenance. [NAS source safety](source-safety.md) applies to every destination and cleanup operation. A backup never authorizes a write to collection files.

[Design overview](../design.md) | [Domain glossary](../../CONTEXT.md)

## Scope and Protection Model

The confirmed first-release boundary is application-state backup, with original collection files protected by external NAS tools. Henshin does not copy, move, delete or restore collection archives/pages, synchronize a second content tree, or manage NAS snapshots. Operators protect those files with NAS/filesystem backup tools using their separately managed writer context. This preserves direct NAS reading and the confirmed read-only source requirement. Content-backup integration would require a separate scope decision.

| Data class | Protection and recovery contract |
| --- | --- |
| Authoritative server state | Full consistent SQLite snapshot, required nonsecret configuration, schema/app versions and instance/library IDs; includes identities, bindings, source snapshots, personal overrides, manifests/fingerprints, accepted events, unresolved candidates and task state |
| Desktop durable state | Separate same-installation backup of its consistent store and nonsecret configuration: installation ID, namespace mappings, reader profiles, pending/held events, unknown intents, saved drafts and command attempts; server backups cannot contain unuploaded local work |
| Derived files | Covers, display caches, rebuildable aggregates/indexes and transient workers are not independent authority. Backup may omit derived files; retain the authoritative data needed to rebuild, and show placeholders when original source bytes no longer exist |
| Secrets | EH cookie contents, owner tokens and desktop connection credentials are excluded. Private snapshots may still contain owner verifiers, gallery locators, native paths and notes; exclusion does not make a backup public |
| Collection bytes | External NAS snapshots and independent file backups, outside Henshin; application backup cannot recreate missing originals |
| Metadata export | Existing versioned UTF-8 export for inspection/portability, with private-field defaults. It is lossy, contains no complete event journal, and is neither restore input nor a content backup |

A long-term application archive is a completed, verified backup bundle deliberately kept outside automatic rotation. It does not remove live entries/history, detach a library, compress/repack books, or implement a cold-storage tier. A historical export may accompany an archive for readability, but cannot replace its database snapshot.

Use separate failure domains: a snapshot on the same NAS helps with some accidental changes, while an independent, preferably offline or immutable off-device copy addresses device loss and compromised writable accounts. RAID and a second directory on the same volume are not independent backups. Henshin can report its own completed/verified artifacts, not certify an external NAS/offsite policy it cannot inspect. Encryption, offsite transfer and immutable storage are operator-managed in this release; there is no cloud upload, key escrow or built-in encryption claim.

## Backup Destinations and Bundle Format

A server administrator registers a destination ID with a native output directory and policy outside every collection root. Clients select that ID, never send arbitrary server output paths. Server-local staging and live databases remain on local disk; a completed bundle may be stored on a separate NAS backup share with write permission limited to that destination. Desktop backups use a local main/native maintenance selection. Apply canonical separation, alias/remount checks and ownership-limited cleanup from source safety before every output/publication/prune operation.

First-release bundles are versioned application containers with required `manifest.json`, `state.sqlite` and `configuration.json` payloads. The concrete container adapter and finite input/output/entry/expansion limits are fixed at G10 before enabling the feature; payload paths and meanings do not depend on source filenames. The manifest records bundle-format version, random artifact ID, originating task/operation ID, destination-local publication order, store kind (server or desktop), instance/library or installation identifiers, originating application/schema versions, snapshot start/completion times, database change revision where applicable, retention class, optional label, payload sizes and SHA-256 digests, included/excluded classes and credential-reset instructions. Read identifiers and revision from the snapshot itself, not a later live query. All restorable application configuration lives in the corresponding SQLite store. `configuration.json` is a nonsecret projection derived from that exact snapshot, never from a later live query or external file; validate agreement on restore rather than letting it override the database. Host service-manager/environment/TLS configuration and secret-store files are not included and must be provisioned separately from the recorded recovery instructions. There is no aggregate configuration-generation counter.

A digest detects corruption relative to the recorded manifest, not authenticity against someone who replaced both. Treat all restore inputs as untrusted containers: enforce bounds and schema versions, allow only defined payloads, reject duplicate/traversal/absolute/link-like entries and unsafe expansion before extraction into private local staging. Never execute bundled scripts or binaries, load SQLite extensions, or follow payload-provided native paths as write destinations. Old application versions required for recovery are obtained independently from trusted release packages; record the version and package checksum/reference alongside the archive.

## Creation, Verification, and Publication

1. Validate owner authorization, namespace, configured destination, retention class and available bounded staging capacity. Capture a task/operation ID and durably reserve a generated artifact ID; serialize backup publication/pruning per destination and store namespace. The owned catalog assigns a monotonically increasing publication order independent of wall-clock time, with aborted reservations permitted to leave gaps. Destination loss blocks the task without using a collection root or deleting an older backup to make space.
2. Produce a consistent SQLite backup through the validated backup API, not a raw copy of a live WAL database. Derive required nonsecret application configuration from this same snapshot, using its settings/mapping/profile records; no live configuration fence or invented generation is needed. Ordinary library writes may continue; the result describes one database snapshot, not the state when serialization finishes. No long live transaction spans network transfer.
3. In private local staging, run SQLite integrity and foreign-key checks plus required singleton/domain/schema validation, including instance identity. Create the manifest and payload digests. Failure leaves current stores and existing backups intact. Do not present an incomplete snapshot as successful.
4. Write a unique temporary artifact beneath the validated destination, finish and flush it, then reread/verify destination payload digests and container completeness. Publish with a same-destination atomic rename and the adapter's validated durability procedure; never rename across filesystems or overwrite a previous good backup. A NAS adapter unable to demonstrate the publication contract cannot claim supported completed backups; use a supported local destination and an external copy workflow instead.
5. Register the completed artifact and finish the task only after publication. Filesystem publication and database registration are not one transaction: after crash, reconcile generated artifacts by manifest/digests and task ownership before registering a published orphan. A truncated/temp artifact remains incomplete. Cancellation before publication leaves only owned staging for safe cleanup; after successful publication, retain the artifact and reconcile/report success rather than deleting it because a late cancellation arrived.
6. Apply an explicitly configured retention policy only after a new completed backup verifies at that destination. A cleanup failure yields a retained backup plus a visible retention warning; it must not invalidate or erase the successful backup.

Completed means a validated artifact was published under the tested destination semantics. It is not a restore drill, independent copy, power-loss guarantee beyond the filesystem adapter, or verification of current NAS content. Expose last successful snapshot time, destination verification time, last restore-drill time (if any), failed/blocked tasks and storage pressure separately.

## Scheduling, Retention, and Long-term Archives

Manual backup works without a schedule. Proposed first-release default after the operator configures a destination: offer daily server backup, disabled until enabled, and a rotating retention policy keeping the latest seven successfully verified rotating bundles per instance/store/destination. The operator sees and confirms the policy when enabling it. The schedule runs only while the service is running; an overdue startup produces at most one catch-up job, not a job for every missed day. A failure does not advance the last-success timestamp. An enabled policy does not promise a 24-hour recovery point when the service or destination is unavailable.

Archive creation is an explicit backup request with retention class `archive` and an optional label. It produces a fresh consistent bundle in a dedicated archive subdirectory of the registered destination. Archive bundles, including manual/pre-upgrade checkpoints deliberately marked archive, never enter rotating retention. They are removed only by explicit operator maintenance outside automatic retention; the first release has no bulk archive-delete command. A rotating backup is not silently promoted to an archive by age, and an export does not become a backup by being retained longer.

Retention uses completed artifact IDs and the catalog publication order, not wall-clock timestamps, user filenames or arbitrary modification times. After catalog loss, preserve artifacts whose safe ordering/ownership cannot be reconciled rather than guessing it from file dates. Before deleting an eligible old rotating bundle, revalidate owned destination, manifest/class, current policy and that the newest verified recovery point remains present. Preserve archives, incomplete/unrecognized files, foreign files, the most recent verified bundle, and required pre-migration rollback material. Low disk space is a failed/blocked backup condition, not permission to prune first or bypass the keep rule. A renamed/remounted or unreadable destination suspends pruning.

After database restore, destination reattachment or loss of artifact-catalog state, discover and verify existing artifacts without pruning. Do not infer deletion authorization from a copied policy or restored catalog. Require explicit operator reconciliation/reactivation of retention; archives remain protected by their manifest class and separate archive namespace. Reconciliation repairs artifact status but never replays a reader action, source mutation or old metadata command.

For long-term readability, retain the manifest, compatible schema/app version information, restore instructions, and optionally a metadata export with its privacy options recorded. Periodically verify retained copies and run a restore drill. Future format migration creates a new verified artifact and retains the original; it never upgrades an archival bundle in place. Keep any external encryption keys and recovery instructions separately and test their availability.

## Server Restore, Migration, and Rollback

Restore remains a stopped-service maintenance operation, never a live HTTP database-replacement route. The operator first stops all writers and the old authority, chooses the intended instance and recovery point, and reviews the estimated lost interval. An application snapshot and a NAS snapshot are not a distributed transaction; record both times when coordinating them. Henshin does not roll collection files backward to match its database.

Validate and stage the bundle outside collection roots under the data-directory lock. Reject a desktop bundle, unsupported/newer schema or malformed/corrupt payload. Preserve the current store/configuration as separate rollback material before replacement; insufficient space blocks restore. Never overwrite the selected backup. Replace only the selected application store after validation, then apply the [credential reset and epoch procedure](architecture.md#authentication-and-secret-handling) and [instance lifecycle](synchronization.md#migration-clone-and-restore): ordinary restore preserves instance/library/entry/event IDs, resets the copied owner verifier and active EH credential reference, requires fresh access credentials/explicit EH reattachment, and starts a fresh authority epoch. Clone mode changes instance identity before serving; it is not a concurrent second authority under the old ID.

Before activation, invalidate restored derived-file references and make every pre-restore server cover/cache artifact unreachable to serving and regeneration lookups; clearing owned derived storage must not touch backups or authoritative records. If that cannot be established, block activation. A later reuse of the same numeric content version cannot reuse bytes from the discarded timeline. Clients observing the new epoch evict old namespace thumbnail bytes and revalidate accepted manifests against that epoch, independently of numeric key equality.

On restored startup, suspend automatic collection scans and external EH work, mark restored server mappings as needing verification, and suspend backup scheduling/publication and rotation until destination/policy reconciliation. Retain database claims and show restored state with a recovery notice. Verify server mappings against current read-only NAS access before explicitly resuming scans; new observations may legitimately be pending/missing. Reconcile tasks with fresh process/mapping/credential generations, never publish an old worker result or accept a checkpoint as fresh evidence. Client mapping/online Open still follows existing epoch refresh, identity and local-access checks; a server mapping needing verification does not prove the client's NAS inaccessible.

Clients refresh authoritative state before online work. Pending immutable events can be redelivered only to their original instance: events present in the restored database deduplicate, missing events for retained entries may insert, and events for absent entries remain held. Previously acknowledged events or metadata changes after the backup point may be unrecoverable. Do not recreate entries by filename or replay old mutating commands to fill the gap. Recovery is rollback, not merge or guaranteed reconstruction.

For an upgrade or rollback, use compatible binaries and a verified pre-migration snapshot; a newer database is not opened by older code. Keep the old store/backup until readiness and an explicit recovery check pass. A verification drill uses an isolated, non-serving maintenance process with scheduling, readers and EH network disabled; any subsequently served test copy must be initialized as a new instance. Never expose a duplicate live authority during a drill.

## Desktop Backup and Recovery

First-release desktop backup is an explicit local maintenance operation while Electron main is stopped and its data-directory lock is held by the maintenance tool. This provides a coherent snapshot of journals, drafts, attempts and configuration without coordinating active Open dispatch. Existing external readers can remain running; backup makes no claim about their state. Use the same verified bundle/publication rules and an independently protected destination. Server scheduling does not back up desktops; show that limitation and the age of the last desktop backup.

Same-installation recovery replaces a stopped desktop store and preserves device ID plus event IDs only when the old installation cannot continue using the same identity/journal. It does not merge with newer local state: preserve that state as rollback material and disclose the lost interval first. Discard the restored display cache and old local derived files; retain journals, drafts and attempts separately. Clear active connection credential references and require explicit authentication; do not silently reuse an accessible old keyring entry. Restore mappings and executable profiles inactive until local paths, executable selections and revisions are reviewed in trusted local setup. No backup can supply a launch permission merely by containing a previously valid executable path.

Prepared/dispatch-unresolved intents become diagnostic Unknown, never replayable launches or active-entry locks. Accepted events retain immutable payloads for normal namespace-scoped redelivery after fresh handshake/authentication; server deduplication still applies. Recovered drafts require fresh-state reapplication, and command attempts require status/current-state reconciliation. A desktop backup cannot contain later unuploaded events; a server backup cannot reconstruct them either. Clearly report this limit rather than claiming complete history recovery.

An independent desktop clone/settings export is a different operation: allocate a new device ID and exclude live launch/event journals, credentials, drafts and command attempts from transfer. Do not duplicate pending work into a second live installation. Operator copying of a whole profile is not a supported clone workflow. The existing [consistency](synchronization.md) and [reader](external-reading.md) rules govern replay and attribution.

## UI and Operation Contracts

Server settings expose configured destination IDs, backup enablement/retention proposals, manual rotating/archive requests, bounded artifact listings, verification tasks and restore instructions. Display store kind, snapshot point, class, validation state, excluded data/secrets and destination policy. Never label an export, an incomplete upload or a same-device-only copy as complete disaster-recovery protection. An explicit authenticated download may save the complete private server bundle to a desktop through the safe client save boundary. Explain its notes, locators, native-path and verifier sensitivity before saving; it is not the redacted metadata export. Local desktop maintenance instructions explain stopping the app, the lock and the separate backup requirement.

[API contracts](api-and-tasks.md) define only authenticated task-based backup/archive creation, artifact listing/verification/download and typed policy selection. Native destination registration and restore remain administrator/native maintenance responsibilities. No endpoint accepts raw source/output paths, restores into a running service, transfers collection content, or installs a backup's executable settings. Recovery-point age and measured restore duration are displayed facts; numerical RPO/RTO guarantees require measured workloads and operational coverage, not merely a schedule setting.

## Acceptance and Evidence

| Scenario | Required result |
| --- | --- |
| Library/configuration changes during backup | Database and configuration projection come from one snapshot, even if live settings change during serialization; restore rejects a conflicting projection |
| Backup policy registered before any artifact exists | Settings read exposes destination IDs, settings revision and inactive/active state without requiring an artifact or revealing secret/native-path data |
| Known credential sentinels in both stores and external secret storage | Published bundles exclude EH/owner-token/connection secret contents; permitted private verifiers/locators remain labeled, and restore clears active authentication references |
| Wall clock moves backward between backups | Retention uses catalog publication order and preserves the newest verified recovery point |
| Older server snapshot restored with newer covers left on disk, then content version reused | Old bytes cannot serve under the reused key; clients observing the new epoch evict/refetch, unavailable accepted sources show placeholders |
| Disk full, NAS disconnect or cancellation at each boundary | Previous good backups and sources survive; incomplete artifacts never appear complete; published orphan reconciles without duplication |
| Crash after publication before task registration, or during pruning | Recover verified artifact status; preserve newest/archived/foreign artifacts and report cleanup uncertainty |
| Restore loses catalog or destination remounts | No automatic pruning; explicit destination/policy reconciliation first |
| Daily schedule misses several days | One catch-up, accurate stale backup age, no invented successful recovery point |
| Archive survives rotation and format upgrade | Original retained unchanged; successor independently verified; source files untouched |
| Tampered/traversing/oversized/wrong-kind/new-schema bundle | Reject before activation or unbounded extraction; existing application store and source remain intact |
| Server restore predates credential rotation and recent events | Old secrets/verifier cannot revive; fresh epoch, recovery notice, mapping verification, task fencing and explicit retention reactivation |
| Restored application state disagrees with current NAS | Reconcile read-only; pending/missing diagnostics, no rollback or repair of collection bytes |
| Stopped desktop backup restored as sole installation | Preserve immutable events, reauthenticate and validate local configuration; Unknown intents and commands never replay |
| Desktop clone or older local snapshot | No duplicated live queue/identity; lost newer local work disclosed, never silently merged |
| Restore drill without NAS or EH credentials | Validate database/identity/events/overrides and rebuildable aggregates in isolation; unavailable covers stay placeholders; no source/network/reader side effect |
| Independent encrypted/offsite copy | Operator retrieves it, verifies bytes, supplies keys and completes isolated restore; Henshin does not claim this occurred from local publication alone |

G2 proves consistent SQLite backup, local durability and migration rollback where first needed. G10 proves container bounds, destination publication/durability, scheduling/retention, archive survival, both store kinds and real restore drills before offering maintenance. G3/G6 source protection remains prerequisite. Record dataset, platform/filesystem, snapshot/verification/drill times, failure injections, recovered identity/history counts, credential-reset results and measured recovery duration. No application backup, restore, NAS snapshot or archive test has yet been executed.
